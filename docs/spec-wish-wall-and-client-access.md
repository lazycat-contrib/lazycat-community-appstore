# Spec: 客户端目录排序、许愿墙与下游用户封禁

状态：已确认
日期：2026-07-30

## 当前假设

1. “建议”“软件上架请求”“软件定制”是许愿墙的三种独立条目，不复用私信或评论数据表。
2. 建议条目仅 `SOFTWARE_ADMIN`、`SITE_ADMIN` 和提交者本人可见；只有两类管理员可以回复和改变状态。
3. 软件上架请求、软件定制条目及管理员回复公开可见，未登录访客也可以浏览。
4. 三类条目只能由懒猫客户端内已识别的用户通过客户端代理提交；服务端浏览器中的登录用户、未登录访客和非懒猫客户端都不能提交。
5. 服务端未登录访客只能浏览公开条目；服务端登录用户同样没有新建入口，管理员只在服务端进行回复和状态处理。
6. 软件定制的联系方式为两个字段：必填邮箱、可选“其他联系方式”自由文本，而不是管理员动态配置的表单字段。
7. 封禁对象是下游客户端用户 ID（`lc_...`），来源于许愿墙或评论；它与服务端注册账号的禁用状态是两套独立机制。
8. 封禁后，携带该客户端用户 ID 的软件源、许愿墙、评论、过期标记和私信请求均被拒绝；历史公开内容保留。
9. 旧客户端同步软件源时不携带客户端用户 ID，因此无法被精确封禁；升级后的客户端会在同步请求中携带稳定的、按源隔离的匿名 ID。
10. 客户端目录默认排序从“默认顺序”改为“最近更新”，并新增“下载最多”。下载量由上游 v2 feed 下发并缓存到客户端。

## Objective

把软件源客户端从单纯的安装器扩展为可向上游商店提交需求的入口，同时让服务端提供一个独立、可公开浏览、可由管理员处理的轻量需求看板“许愿墙”。服务端还必须能从许愿墙或评论定位下游客户端用户，并阻止该用户继续接入软件源。

目标用户：

- 下游客户端用户：按更新时间或下载量找应用，提交建议、上架请求和定制需求。
- 普通站点访客：浏览公开的上架请求和定制需求。
- 软件管理员和站点管理员：查看全部需求、回复、更新状态、封禁恶意下游用户。

## Functional Contract

### 1. 客户端应用目录排序

- 初次进入“软件安装”时，默认 `sortMode = recent`，以应用实际软件更新时间倒序排列。
- 排序选项至少包括：最近更新、下载最多、名称、软件源。
- “下载最多”按累计下载量倒序；相同时依次按更新时间倒序、名称升序，保证顺序稳定。
- v2 feed 为每个应用增加累计下载量字段；客户端同步后持久化该字段。
- 不改变 v1 feed；不支持下载量字段的第三方源按 0 处理。

### 2. 许愿墙数据与流程

条目类型：

| 类型 | 可见范围 | 提交字段 | 回复权限 |
|---|---|---|---|
| 建议 `SUGGESTION` | 提交者、软件管理员、站点管理员 | 标题、说明 | 软件管理员、站点管理员 |
| 软件上架请求 `APP_REQUEST` | 所有人，包括未登录访客 | 软件名、说明、参考链接（可选） | 软件管理员、站点管理员 |
| 软件定制 `CUSTOMIZATION` | 所有人，包括未登录访客 | 标题、说明、邮箱、其他联系方式（可选） | 软件管理员、站点管理员 |

- 条目状态：`OPEN`、`PLANNED`、`IN_PROGRESS`、`COMPLETED`、`REJECTED`。
- 新建条目默认为 `OPEN`。
- 新建时提交者必须输入非空的初始状态说明；服务端保存一条 `OPEN` 状态历史，记录操作人、状态说明和时间。
- 每次状态更新都必须由操作管理员输入非空的状态说明；状态历史不可覆盖，按时间展示每次状态、说明和操作人。
- 管理员可回复并改变状态；回复跟随条目的可见范围。
- 普通提交者不能编辑管理员回复或状态。
- 列表支持类型、状态筛选，默认按最后活动时间倒序。
- 公开接口绝不返回建议条目，也不返回定制需求的邮箱和其他联系方式。
- 联系方式仅提交者本人和两类管理员可见。
- 条目保存提交来源（站内用户或下游客户端）、显示名、客户端用户 ID（如有）和时间。

### 3. 服务端入口与权限

- 服务端增加顶级导航“许愿墙”，页面独立于聊天页面和现有评论通知。
- 未登录时，许愿墙只显示“软件上架请求”“软件定制”两个公开分区，不出现“建议”入口或数据。
- 登录后的普通站点用户可看到公开分区，但服务端不提供新建入口；通过懒猫客户端提交过建议的同一身份可在客户端查看本人建议。
- `SOFTWARE_ADMIN`、`SITE_ADMIN` 可看到全部三类条目、待处理数量、回复和状态操作。
- 新的许愿墙条目对管理员形成未处理提醒；提醒入口跳转到许愿墙，而不是进入聊天会话。

### 4. 客户端提交入口

- 客户端“软件安装”页增加“许愿墙”按钮。
- 多软件源场景先选择目标上游；只列出 v2 feed 声明支持许愿墙的源。
- 只有客户端能提供已识别懒猫用户身份且存在设备 ID 时才允许提交；本地模式、普通浏览器和未认证客户端只可查看公开条目。
- 客户端通过本地 Go 服务代理上游许愿墙 API，不直接从浏览器跨域提交。
- 代理沿用评论协议，发送按源隔离的 `X-LazyCat-Client-User-ID`、显示名和客户端代理标识。
- 提交成功后展示条目编号与当前状态，并可从客户端查看该源允许当前用户看到的条目和回复。

### 5. 下游客户端用户封禁

- 新增独立的“下游用户”管理数据，以客户端用户 ID 为唯一键，包含显示名、首次/最近出现时间、来源（评论/许愿墙）、封禁状态、原因和操作时间。
- 许愿墙管理视图和评论管理操作均可跳转/触发“封禁此下游用户”。
- 仅 `SITE_ADMIN` 可封禁或解封；软件管理员可以查看 ID 和封禁状态，但不能执行封禁。
- 客户端同步软件源时发送与评论/许愿墙相同的按源隔离用户 ID。
- `/source/v2/index.json` 在密码和分组计算前检查该 ID；命中封禁时返回 `403 CLIENT_BLOCKED`，不返回 feed。
- 被封禁用户调用许愿墙、评论、过期标记、私信等客户端代理接口时同样返回 `403 CLIENT_BLOCKED`。
- 客户端把 `CLIENT_BLOCKED` 显示为明确的“已被该软件源封禁”，不误报为网络或密码错误。

## Tech Stack

- 服务端：Go 1.26、`net/http`、ent，支持 SQLite/PostgreSQL/MySQL。
- 客户端本地服务：Go、ent SQLite 缓存、上游 HTTP 代理。
- Web：React 19、TypeScript 5.9、Vite 7、AstryX 组件。
- 协议：现有 `/source/v2/index.json` 与 `/api/v1` JSON API，增量向后兼容。

## Code Style

Go handler 保持薄层，权限和规范化逻辑下沉到可测试函数；错误继续使用稳定错误码：

```go
if s.clientUserBlocked(r.Context(), clientUserID) {
	writeError(w, http.StatusForbidden, "CLIENT_BLOCKED", "This client user is blocked", nil)
	return
}
```

React 使用显式联合类型，不用散落字符串：

```ts
export type WishKind = 'SUGGESTION' | 'APP_REQUEST' | 'CUSTOMIZATION';
export type WishStatus = 'OPEN' | 'PLANNED' | 'IN_PROGRESS' | 'COMPLETED' | 'REJECTED';
```

## Testing Strategy

- 单元测试：排序稳定性、字段清洗、公开 DTO 脱敏、角色/来源判断、封禁判断。
- 服务端集成测试：匿名/普通用户/软件管理员/站点管理员的矩阵；公开列表不泄漏建议和联系方式；回复与状态权限；封禁/解封。
- 源协议测试：v2 下载量、能力声明、身份头、`CLIENT_BLOCKED`、没有身份头的旧客户端兼容。
- 客户端服务测试：多源路由、代理身份头、上游错误透传、下载量缓存迁移。
- 前端契约测试：默认 recent、downloads 选项、匿名许愿墙导航、管理员操作、封禁按钮仅在客户端作者记录出现。
- 完成前运行全部 Go 测试、race 测试、前端测试、生产构建和 OpenAPI 校验。

## Boundaries

- Always：输入长度限制、邮箱格式校验、公开 DTO 脱敏、分页、稳定错误码、数据库索引、角色权限测试。
- Ask first：改变三类可见范围、开放非懒猫客户端提交、改变谁能封禁、删除条目或状态历史。
- Never：把联系方式写入 v2 feed；用显示名代替稳定客户端用户 ID；让前端隐藏代替后端权限；从封禁操作级联删除历史评论或许愿。

## Success Criteria

- 客户端软件安装页首次打开默认显示最近更新，且可按累计下载量排序。
- 三类许愿只能从支持该能力且已识别懒猫用户的客户端提交到选定上游；服务端和普通浏览器提交均被后端拒绝。
- 未登录服务端访客只能看到公开上架请求与定制需求，不能通过 API 枚举建议或联系方式。
- 两类管理员可以处理全部许愿；普通用户只能访问许可范围内的数据。
- 新建条目和每次状态更新都产生包含状态、非空状态说明、操作人和时间的不可覆盖历史记录。
- 管理员能从许愿墙或评论识别同一个客户端用户 ID；站点管理员可封禁/解封。
- 新客户端被封禁后无法继续同步该源，也无法继续提交互动；客户端显示明确原因。
- 旧 v1 feed 和不含新字段的第三方 v2 feed 仍能正常同步。
- 所有验证命令通过，OpenAPI 与实现同步。

## Confirmed Decisions

1. 许愿只能通过懒猫客户端提交；非懒猫用户和服务端浏览器用户不能提交。
2. 建议对提交者本人以及软件管理员、站点管理员可见。
3. 状态采用 `OPEN`、`PLANNED`、`IN_PROGRESS`、`COMPLETED`、`REJECTED`；新建和每次状态更新都必须填写状态说明并保存操作历史。

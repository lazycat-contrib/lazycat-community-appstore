# Wish Wall Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an independent Wish Wall where only identified LazyCat client users can submit suggestions, app requests, and customization requests, while the server UI provides privacy-aware browsing and administrator processing with immutable status notes.

**Architecture:** Store wishes, replies, and status events as separate ent entities. The public server API serves visibility-filtered reads, a trusted-client-only create endpoint accepts proxied LazyCat identity, and administrator endpoints add replies or status transitions. Advertise capability in feed v2 and proxy client UI requests through the standalone Go service.

**Tech Stack:** Go 1.26, net/http, ent, SQLite/PostgreSQL/MySQL, React 19, TypeScript 5.9, AstryX, OpenAPI 3.

## Global Constraints

- Only requests with trusted client proxy headers, a non-empty LazyCat device ID, and a non-local client identity may create wishes.
- Server sessions, anonymous browsers, local standalone mode, and non-LazyCat clients cannot create wishes.
- `SUGGESTION` is visible only to its client submitter and software/site administrators.
- `APP_REQUEST` and `CUSTOMIZATION` content/status/replies are public; contact fields are never public.
- Creation and every status transition require a non-empty status note and append immutable history.
- Administrators may reply and change status; ordinary users cannot.
- No new runtime dependency.

- `client/src/modules/wishwall/WishWall.tsx`: shared board/list/detail/status history view.

- `docs/openapi.yaml`, `docs/openapi_test.go`: API contract.
